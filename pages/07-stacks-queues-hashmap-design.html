Circular Queue

Q1. Discuss how you would implement a Circular Queue. (Asked twice in the original list.)
LeetCode: Design Circular Queue ↗

Problem statement: Implement a fixed-capacity Circular Queue supporting enqueue (add to the back) and dequeue (remove from the front) operations, both in O(1) time, using a fixed-size backing array WITHOUT shifting elements on every dequeue.

Approach: rather than always inserting at a growing array index and shifting elements after every removal (which a naive array-backed queue would require), a circular queue tracks separate frontIndex and rearIndex pointers, and WRAPS them back to 0 using the modulo operator whenever they reach the end of the backing array -- allowing the array's available slots to be REUSED indefinitely as elements are added and removed, without ever shifting existing elements.

public class CircularQueue {
 
    private final int[] backingArray;
    private final int queueCapacity;
    private int frontIndex;
    private int elementCount;
 
    public CircularQueue(int queueCapacity) {
        this.queueCapacity = queueCapacity;
        this.backingArray = new int[queueCapacity];
        this.frontIndex = 0;
        this.elementCount = 0;
    }
 
    public boolean enqueue(int newValue) {
        if (isFull()) {
            return false; // queue is at capacity -- cannot add more
        }
        // compute the next free slot, WRAPPING AROUND to the start of the
        // array once the end is reached
        int insertionIndex = (frontIndex + elementCount) % queueCapacity;
        backingArray[insertionIndex] = newValue;
        elementCount++;
        return true;
    }
 
    public int dequeue() {
        if (isEmpty()) {
            throw new IllegalStateException("Cannot dequeue from an empty queue");
        }
        int removedValue = backingArray[frontIndex];
        // advance frontIndex, WRAPPING AROUND rather than shifting every
        // remaining element -- this is the key optimization over a naive
        // array-backed queue
        frontIndex = (frontIndex + 1) % queueCapacity;
        elementCount--;
        return removedValue;
    }
 
    public boolean isFull() {
        return elementCount == queueCapacity;
    }
 
    public boolean isEmpty() {
        return elementCount == 0;
    }
 
    public static void main(String[] arguments) {
        CircularQueue myQueue = new CircularQueue(3);
        myQueue.enqueue(10);
        myQueue.enqueue(20);
        myQueue.enqueue(30);
        System.out.println(myQueue.isFull()); // true
 
        System.out.println(myQueue.dequeue()); // 10
        myQueue.enqueue(40); // reuses the now-free slot that held "10", wrapping around
        System.out.println(myQueue.dequeue()); // 20
        System.out.println(myQueue.dequeue()); // 30
        System.out.println(myQueue.dequeue()); // 40
    }
}
Note: The key insight worth articulating clearly in an interview: a naive array-backed queue that always dequeues from index 0 must shift every remaining element left by one position on every dequeue, costing O(n) per removal. The circular queue's wraparound technique (using the modulo operator to compute both the insertion point and the new front index) achieves the SAME functional behavior in O(1) per operation, by treating the backing array as if its end were logically connected back to its beginning.

Complexity: O(1) time for both enqueue and dequeue, O(capacity) total space.

Producer/Consumer: A Custom BlockingQueue

Q2. Code a custom BlockingQueue in Java to implement the Producer/Consumer problem.
LeetCode: Design Bounded Blocking Queue ↗

Problem statement: Implement a thread-safe, fixed-capacity BlockingQueue from scratch, to be shared between one or more PRODUCER threads (which add items) and one or more CONSUMER threads (which remove items). A producer attempting to add to a FULL queue should BLOCK (wait) until space becomes available; a consumer attempting to remove from an EMPTY queue should BLOCK until an item becomes available.

Approach: use a plain LinkedList as the backing storage, guarded by synchronized blocks, combined with wait() and notifyAll() (the standard Java inter-thread communication mechanism, covered in the earlier Multithreading document in this interview-guide series) to correctly implement the blocking behavior on both the producer and consumer sides.

import java.util.LinkedList;
import java.util.Queue;
 
public class CustomBlockingQueue<ElementType> {
 
    private final Queue<ElementType> backingQueue = new LinkedList<>();
    private final int queueCapacity;
 
    public CustomBlockingQueue(int queueCapacity) {
        this.queueCapacity = queueCapacity;
    }
 
    // Called by PRODUCER threads to add a new item
    public synchronized void put(ElementType newItem) throws InterruptedException {
        // wait (releasing the lock while waiting) while the queue is full
        while (backingQueue.size() == queueCapacity) {
            wait();
        }
 
        backingQueue.offer(newItem);
 
        // wake up any CONSUMER thread that might be waiting for an item to appear
        notifyAll();
    }
 
    // Called by CONSUMER threads to remove and return the next item
    public synchronized ElementType take() throws InterruptedException {
        // wait (releasing the lock while waiting) while the queue is empty
        while (backingQueue.isEmpty()) {
            wait();
        }
 
        ElementType removedItem = backingQueue.poll();
 
        // wake up any PRODUCER thread that might be waiting for space to free up
        notifyAll();
 
        return removedItem;
    }
 
    public static void main(String[] arguments) throws InterruptedException {
        CustomBlockingQueue<Integer> sharedQueue = new CustomBlockingQueue<>(5);
 
        Thread producerThread = new Thread(() -> {
            try {
                for (int itemValue = 1; itemValue <= 10; itemValue++) {
                    sharedQueue.put(itemValue);
                    System.out.println("Produced: " + itemValue);
                }
            } catch (InterruptedException interruptedException) {
                Thread.currentThread().interrupt();
            }
        });
 
        Thread consumerThread = new Thread(() -> {
            try {
                for (int count = 0; count < 10; count++) {
                    int consumedValue = sharedQueue.take();
                    System.out.println("Consumed: " + consumedValue);
                }
            } catch (InterruptedException interruptedException) {
                Thread.currentThread().interrupt();
            }
        });
 
        producerThread.start();
        consumerThread.start();
        producerThread.join();
        consumerThread.join();
    }
}
Note: Two details worth highlighting explicitly in an interview: (1) wait() must ALWAYS be called inside a WHILE loop re-checking the condition, never a plain if -- a thread woken by notifyAll() must re-verify the condition still holds, since another thread could have changed it first (covered in more detail in the Multithreading document earlier in this series). (2) notifyAll() is used rather than notify() specifically because there may be MULTIPLE waiting producers AND consumers simultaneously; notify() only wakes ONE arbitrary waiting thread, which could incorrectly wake a thread that's still waiting for the WRONG condition (e.g. waking another producer when a CONSUMER was the one that needed to proceed), causing that thread to go back to sleep and potentially stall the system. In real production code, java.util.concurrent.BlockingQueue's own battle-tested implementations (like ArrayBlockingQueue or LinkedBlockingQueue) should be used instead of a hand-rolled version like this one -- this exercise exists specifically to demonstrate understanding of the underlying wait/notify mechanics that those built-in classes are built on.

Complexity: O(1) time per put() or take() call (excluding any time spent actually blocked/waiting). O(capacity) total space.

Stack Modification

Q3. Stack modification based question.

Problem statement: A commonly-asked "stack modification" exercise: given a stack, sort its elements into ASCENDING order using only stack operations (push and pop) and, at most, ONE additional temporary stack -- no other data structure (like an array or ArrayList) may be used.

import java.util.ArrayDeque;
import java.util.Deque;
 
public class StackSorter {
 
    public static void sortStackAscending(Deque<Integer> originalStack) {
        Deque<Integer> temporaryStack = new ArrayDeque<>();
 
        while (!originalStack.isEmpty()) {
            int currentValue = originalStack.pop();
 
            // move elements from temporaryStack back into originalStack as
            // long as they are GREATER than currentValue, making room to
            // insert currentValue in its correctly-sorted position
            while (!temporaryStack.isEmpty() && temporaryStack.peek() > currentValue) {
                originalStack.push(temporaryStack.pop());
            }
 
            temporaryStack.push(currentValue);
        }
 
        // temporaryStack now holds every element in sorted order (smallest on
        // top) -- transfer it back into originalStack so the RESULT also has
        // the smallest element on top, matching a conventional sorted stack
        while (!temporaryStack.isEmpty()) {
            originalStack.push(temporaryStack.pop());
        }
    }
 
    public static void main(String[] arguments) {
        Deque<Integer> myStack = new ArrayDeque<>();
        myStack.push(5);
        myStack.push(1);
        myStack.push(4);
        myStack.push(2);
        myStack.push(3);
 
        sortStackAscending(myStack);
 
        while (!myStack.isEmpty()) {
            System.out.print(myStack.pop() + " ");
        }
        // 1 2 3 4 5
    }
}

Complexity: O(n^2) time in the worst case (each of the n elements may need to be moved back and forth across the two stacks multiple times), O(n) extra space for the temporary stack.

Building a HashMap from Scratch

Q4. Create a HashMap (using generics).
LeetCode: Design Hashmap ↗

Problem statement: Implement a simplified, GENERIC HashMap class from scratch, supporting put(key, value), get(key), and remove(key), using separate chaining to resolve hash collisions (as described conceptually in the Java Interview Guide document series' Collections Internals discussion).

import java.util.LinkedList;
 
public class CustomHashMap<KeyType, ValueType> {
 
    // A single key-value entry stored within a bucket's chain
    private static class MapEntry<KeyType, ValueType> {
        KeyType entryKey;
        ValueType entryValue;
 
        MapEntry(KeyType entryKey, ValueType entryValue) {
            this.entryKey = entryKey;
            this.entryValue = entryValue;
        }
    }
 
    private final LinkedList<MapEntry<KeyType, ValueType>>[] bucketArray;
    private final int bucketCount;
 
    @SuppressWarnings("unchecked")
    public CustomHashMap(int bucketCount) {
        this.bucketCount = bucketCount;
        this.bucketArray = new LinkedList[bucketCount];
        for (int index = 0; index < bucketCount; index++) {
            bucketArray[index] = new LinkedList<>();
        }
    }
 
    // Computes which bucket a given key belongs in, based on its hashCode()
    private int computeBucketIndex(KeyType targetKey) {
        int rawHashCode = targetKey.hashCode();
        // Math.abs guards against a negative hashCode() producing a negative
        // (invalid) array index
        return Math.abs(rawHashCode) % bucketCount;
    }
 
    public void put(KeyType targetKey, ValueType newValue) {
        int bucketIndex = computeBucketIndex(targetKey);
        LinkedList<MapEntry<KeyType, ValueType>> targetBucket = bucketArray[bucketIndex];
 
        // check whether this key ALREADY exists in the bucket -- if so, update it
        for (MapEntry<KeyType, ValueType> existingEntry : targetBucket) {
            if (existingEntry.entryKey.equals(targetKey)) {
                existingEntry.entryValue = newValue;
                return;
            }
        }
        // key not found in the bucket -- add a brand new entry
        targetBucket.add(new MapEntry<>(targetKey, newValue));
    }
 
    public ValueType get(KeyType targetKey) {
        int bucketIndex = computeBucketIndex(targetKey);
        LinkedList<MapEntry<KeyType, ValueType>> targetBucket = bucketArray[bucketIndex];
 
        for (MapEntry<KeyType, ValueType> currentEntry : targetBucket) {
            if (currentEntry.entryKey.equals(targetKey)) {
                return currentEntry.entryValue;
            }
        }
        return null; // key not found
    }
 
    public boolean remove(KeyType targetKey) {
        int bucketIndex = computeBucketIndex(targetKey);
        LinkedList<MapEntry<KeyType, ValueType>> targetBucket = bucketArray[bucketIndex];
 
        return targetBucket.removeIf(currentEntry -> currentEntry.entryKey.equals(targetKey));
    }
 
    public static void main(String[] arguments) {
        CustomHashMap<String, Integer> myMap = new CustomHashMap<>(16);
        myMap.put("apples", 50);
        myMap.put("bananas", 30);
 
        System.out.println(myMap.get("apples")); // 50
        myMap.put("apples", 75); // updates the existing entry
        System.out.println(myMap.get("apples")); // 75
 
        myMap.remove("bananas");
        System.out.println(myMap.get("bananas")); // null
    }
}
Note: This simplified implementation omits DYNAMIC RESIZING (growing the bucket array and rehashing every entry once a load-factor threshold is exceeded, exactly as covered for the real java.util.HashMap in the Collections Internals discussion earlier in this interview-guide series). A more advanced follow-up to this exercise commonly asks the candidate to add that resizing behavior -- doubling bucketArray's size and re-inserting every existing entry into the new, larger array whenever the map's total entry count exceeds roughly 0.75 times the current bucket count.

Complexity: O(1) average-case time for put(), get(), and remove(), assuming a reasonably well-distributed hashCode() implementation for the key type and a bucket count that stays proportional to the number of stored entries -- exactly mirroring the real java.util.HashMap's own performance characteristics.

Dynamic Programming: House Robber

Q5. Dynamic programming: the House Robber problem (HackerRank).
LeetCode: House Robber ↗

Problem statement: A robber plans to rob houses along a street, where each house holds a certain amount of money, given as an array. The robber CANNOT rob two ADJACENT houses (doing so triggers an alarm). Determine the MAXIMUM total amount of money that can be robbed without robbing two adjacent houses. Example: calculateMaximumRobberyAmount({2, 7, 9, 3, 1}) should return 12 (rob house 0 for 2, house 2 for 9, and house 4 for 1 -- total 12; alternatively, robbing house 1 for 7 and house 3 for 3, plus house 0's 2, is not better).

Approach: at each house, the robber has exactly two choices: SKIP this house (carrying forward the best total achievable up to the PREVIOUS house), or ROB this house (adding its value to the best total achievable up to TWO houses back, since the immediately preceding house cannot also be robbed). Take whichever choice yields the larger total.

public class HouseRobberCalculator {
 
    public static int calculateMaximumRobberyAmount(int[] houseValues) {
        if (houseValues.length == 0) {
            return 0;
        }
        if (houseValues.length == 1) {
            return houseValues[0];
        }
 
        // bestAmountRobbingUpTo[i] = maximum amount robbable considering only
        // houses 0 through i
        int[] bestAmountRobbingUpTo = new int[houseValues.length];
        bestAmountRobbingUpTo[0] = houseValues[0];
        bestAmountRobbingUpTo[1] = Math.max(houseValues[0], houseValues[1]);
 
        for (int houseIndex = 2; houseIndex < houseValues.length; houseIndex++) {
            // option 1: skip this house -- carry forward the previous best
            int bestIfSkippingThisHouse = bestAmountRobbingUpTo[houseIndex - 1];
 
            // option 2: rob this house -- add its value to the best total
            // from TWO houses back (since the immediately previous house
            // cannot ALSO be robbed)
            int bestIfRobbingThisHouse = bestAmountRobbingUpTo[houseIndex - 2] + houseValues[houseIndex];
 
            bestAmountRobbingUpTo[houseIndex] = Math.max(bestIfSkippingThisHouse, bestIfRobbingThisHouse);
        }
 
        return bestAmountRobbingUpTo[houseValues.length - 1];
    }
 
    public static void main(String[] arguments) {
        int[] houseValues = {2, 7, 9, 3, 1};
        System.out.println(calculateMaximumRobberyAmount(houseValues)); // 12
    }
}
Note: This solution can be optimized from O(n) extra space down to O(1), since at any point it only ever needs the two MOST RECENT values from the bestAmountRobbingUpTo array -- exactly the same space-optimization pattern used for the iterative Fibonacci solution in Document 1 of this series, since House Robber's recurrence has the identical two-steps-back structure.
public class HouseRobberCalculator {
 
    // Space-optimized version: O(1) extra space, keeping only the two most
    // recently computed values rather than the full array
    public static int calculateMaximumRobberyAmountOptimized(int[] houseValues) {
        int bestTwoHousesBack = 0;
        int bestOneHouseBack = 0;
 
        for (int currentHouseValue : houseValues) {
            int bestIncludingCurrentHouse = Math.max(
                bestOneHouseBack,                              // skip this house
                bestTwoHousesBack + currentHouseValue);        // rob this house
 
            bestTwoHousesBack = bestOneHouseBack;
            bestOneHouseBack = bestIncludingCurrentHouse;
        }
        return bestOneHouseBack;
    }
 
    public static void main(String[] arguments) {
        System.out.println(calculateMaximumRobberyAmountOptimized(new int[]{2, 7, 9, 3, 1})); // 12
    }
}

Complexity: O(n) time for both versions. O(n) extra space for the table-based version; O(1) extra space for the optimized version.
