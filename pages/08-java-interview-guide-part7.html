Java Interview Guide — Part 7

Programming &amp; Coding Interview Questions — Full Solutions

This is Part 7, the final part, of a 7-part Java interview preparation guide. The original source material listed these as bare problem prompts with no code or explanation — a typical "practice list" an interviewer might draw from. Every problem below has been given a complete problem statement, a worked Java solution, a complexity analysis, and an explanation of the approach.

Where a problem is conceptual rather than algorithmic (e.g. comparing String/StringBuilder/StringBuffer), a full written answer is given instead of code.

Array & String Problems

Q1. Swap two integers without using extra space (no temporary variable).

Problem: Given two integer variables, swap their values without declaring a third (temporary) variable.

Approach: Use arithmetic (addition/subtraction) or the bitwise XOR trick. XOR is generally preferred in interviews because it avoids the (admittedly unlikely in modern Java) risk of integer overflow that the addition/subtraction approach has with very large values.

public class SwapWithoutExtraSpace {
 
    public static void swapUsingXor(int[] numbers, int firstIndex, int secondIndex) {
        if (firstIndex == secondIndex) {
            return; // XOR-swapping a value with itself would zero it out -- guard against this
        }
        numbers[firstIndex] = numbers[firstIndex] ^ numbers[secondIndex];
        numbers[secondIndex] = numbers[firstIndex] ^ numbers[secondIndex];
        numbers[firstIndex] = numbers[firstIndex] ^ numbers[secondIndex];
    }
 
    public static void main(String[] args) {
        int[] values = {5, 12};
        swapUsingXor(values, 0, 1);
        System.out.println(values[0] + ", " + values[1]); // 12, 5
    }
}

Why it works: XOR-ing a value with itself always produces 0, and XOR-ing any value with 0 returns that value unchanged. Working through it: after step 1, numbers[firstIndex] holds (a XOR b). After step 2, numbers[secondIndex] becomes (a XOR b) XOR b = a. After step 3, numbers[firstIndex] becomes (a XOR b) XOR a = b. The two values have swapped.

Note: This trick is a common interview talking point, but it's rarely used in real production code — a plain temporary variable is clearer, and on modern hardware the XOR version isn't meaningfully faster. It's also NOT safe if firstIndex == secondIndex refers to the same memory location (as guarded above), and it doesn't generalize to non-integer types.

Complexity: O(1) time, O(1) extra space.

Q2. Reverse a string using a HashMap-based approach.
LeetCode: Related: Reverse String ↗

Problem: Reverse the characters of a string. (The original prompt specifically mentions using a HashMap; the most natural HashMap-flavored approach is to record each character's original index, though a two-pointer swap is simpler and more efficient for plain reversal — both are shown below for comparison.)

import java.util.LinkedHashMap;
import java.util.Map;
 
public class ReverseStringWithMap {
 
    // HashMap-based approach: map each position to its character, then
    // rebuild the string by reading the map's keys in reverse order.
    public static String reverseUsingMap(String inputText) {
        Map<Integer, Character> indexToCharacter = new LinkedHashMap<>();
        for (int index = 0; index < inputText.length(); index++) {
            indexToCharacter.put(index, inputText.charAt(index));
        }
 
        StringBuilder reversedBuilder = new StringBuilder();
        for (int index = inputText.length() - 1; index >= 0; index--) {
            reversedBuilder.append(indexToCharacter.get(index));
        }
        return reversedBuilder.toString();
    }
 
    public static void main(String[] args) {
        System.out.println(reverseUsingMap("interview")); // weivretni
    }
}
Note: A HashMap is not actually the natural data structure for this problem — it adds O(n) extra space and hashing overhead for no real benefit here. It's included because it was explicitly asked for, but in a real interview it's worth mentioning the simpler, more efficient two-pointer approach shown in the next question, and explaining why it's preferable.

Complexity (HashMap approach): O(n) time, O(n) extra space (for the map and the StringBuilder).

Q3. Convert a decimal number to its binary representation.

Problem: Given a non-negative decimal integer, produce its binary (base-2) string representation, without using a built-in conversion method.

Approach: Repeatedly divide the number by 2, recording the remainder (0 or 1) at each step — these remainders, read in reverse order (last computed to first), form the binary representation. A stack (or simply prepending to a StringBuilder) naturally reverses this order for you.

public class DecimalToBinary {
 
    public static String convertToBinary(int decimalValue) {
        if (decimalValue == 0) {
            return "0";
        }
 
        StringBuilder binaryBuilder = new StringBuilder();
        int remainingValue = decimalValue;
 
        while (remainingValue > 0) {
            int currentBit = remainingValue % 2;
            binaryBuilder.insert(0, currentBit); // prepend -- builds the string in correct order
            remainingValue = remainingValue / 2;
        }
        return binaryBuilder.toString();
    }
 
    public static void main(String[] args) {
        System.out.println(convertToBinary(13));  // 1101
        System.out.println(convertToBinary(0));   // 0
        System.out.println(convertToBinary(255)); // 11111111
 
        // Built-in equivalent, for comparison:
        System.out.println(Integer.toBinaryString(13)); // 1101
    }
}

Complexity: O(log n) time (the number of bits needed is proportional to log2(n)), O(log n) space for the result string.

Q4. Return the size (length) of the last word in a sentence.
LeetCode: Length Of Last Word ↗

Problem: Given a string consisting of words separated by spaces, return the length of the last word. Example: "Hello World" -> 5. "Hello " (trailing space) -> 5. "" (empty string) -> 0.

Approach: The cleanest approach walks backward from the end of the string: first skip any trailing spaces, then count characters until the next space (or the start of the string) is reached.

public class LastWordLength {
 
    public static int lengthOfLastWord(String sentence) {
        int index = sentence.length() - 1;
 
        // skip any trailing spaces
        while (index >= 0 && sentence.charAt(index) == ' ') {
            index--;
        }
 
        int lastWordLength = 0;
        // count backward through the last word's characters
        while (index >= 0 && sentence.charAt(index) != ' ') {
            lastWordLength++;
            index--;
        }
 
        return lastWordLength;
    }
 
    public static void main(String[] args) {
        System.out.println(lengthOfLastWord("Hello World")); // 5
        System.out.println(lengthOfLastWord("Hello "));      // 5
        System.out.println(lengthOfLastWord(""));            // 0
        System.out.println(lengthOfLastWord("   "));         // 0
    }
}

Complexity: O(n) time in the worst case, O(1) extra space.

Q5. Given a number greater than 9, repeatedly sum its digits until the result is a single digit less than 10 (the "digital root").
LeetCode: Add Digits ↗

Problem: For example, 38 -> 3+8 = 11 -> 1+1 = 2. Stop once the result is less than 10.

public class DigitalRoot {
 
    public static int computeDigitalRoot(int inputNumber) {
        int currentValue = inputNumber;
 
        while (currentValue >= 10) {
            int digitSum = 0;
            int remainingValue = currentValue;
 
            while (remainingValue > 0) {
                digitSum += remainingValue % 10; // extract the last digit and add it
                remainingValue /= 10;             // drop the last digit
            }
            currentValue = digitSum;
        }
        return currentValue;
    }
 
    public static void main(String[] args) {
        System.out.println(computeDigitalRoot(38)); // 2   (38 -> 11 -> 2)
        System.out.println(computeDigitalRoot(9875)); // 2 (9875 -> 29 -> 11 -> 2)
    }
}
Note: There's also an elegant O(1) constant-time formula for the digital root, based on modular arithmetic: for inputNumber > 0, the digital root equals 1 + (inputNumber - 1) % 9. This is a fun fact worth mentioning after presenting the iterative solution above, but the iterative version is what most interviewers are actually looking for, since it demonstrates the digit-extraction technique.

Complexity: O(log n) per digit-summing pass, and the number of passes needed is small in practice (at most a small constant number of iterations for any realistic input size) — effectively O(log n) overall.

Sorting, Searching & Recursion

Q6. Implement counting sort.
LeetCode: Related: Sort Colors ↗

Problem: Sort an array of non-negative integers using counting sort — an efficient, non-comparison-based sorting algorithm that works well when the range of possible values is small relative to the number of elements.

Approach: Counting sort works by counting how many times each distinct value appears, then using those counts to place each value directly into its correct position in the output — never comparing two elements against each other, which is what lets it beat the O(n log n) lower bound that applies to comparison-based sorts.

public class CountingSort {
 
    public static int[] countingSort(int[] inputValues) {
        if (inputValues.length == 0) {
            return inputValues;
        }
 
        int maxValue = java.util.Arrays.stream(inputValues).max().getAsInt();
 
        // countOfValue[v] will hold how many times value v appears in the input
        int[] countOfValue = new int[maxValue + 1];
        for (int value : inputValues) {
            countOfValue[value]++;
        }
 
        // convert counts into a running total, so countOfValue[v] becomes
        // "how many values are <= v" -- this tells us the correct output position
        for (int value = 1; value <= maxValue; value++) {
            countOfValue[value] += countOfValue[value - 1];
        }
 
        int[] sortedResult = new int[inputValues.length];
        // walk the input backward to keep the sort stable (equal elements keep their relative order)
        for (int i = inputValues.length - 1; i >= 0; i--) {
            int currentValue = inputValues[i];
            int outputPosition = countOfValue[currentValue] - 1;
            sortedResult[outputPosition] = currentValue;
            countOfValue[currentValue]--;
        }
        return sortedResult;
    }
 
    public static void main(String[] args) {
        int[] unsorted = {4, 2, 2, 8, 3, 3, 1};
        int[] sorted = countingSort(unsorted);
        System.out.println(java.util.Arrays.toString(sorted)); // [1, 2, 2, 3, 3, 4, 8]
    }
}

Complexity: O(n + k) time and space, where n is the number of elements and k is the range of input values (maxValue + 1). This beats the O(n log n) lower bound of comparison-based sorts, but only pays off when k is not significantly larger than n — for a huge value range with relatively few elements, a comparison sort (or radix sort) is a better fit.

Linked Lists & Data Structure Design

Q7. What are the differences between an Array and an ArrayList in Java?

This is a conceptual question rather than a coding one:

  • Size — an array has a fixed size, set at creation and never changeable. ArrayList grows and shrinks dynamically as elements are added or removed.
  • Type — an array can hold primitives directly (int[], double[]) as well as objects. ArrayList can only hold objects (autoboxing handles primitives transparently, e.g. ArrayList<Integer>, but under the hood every element is still a boxed object).
  • API — an array offers minimal built-in functionality (just length and index access via []). ArrayList (as part of the Collections Framework) offers a rich API: add(), remove(), contains(), indexOf(), and interoperability with the rest of java.util.
  • Performance — a raw array has marginally less overhead than an ArrayList for simple index-based access, since ArrayList carries some object overhead and (for boxed primitives) autoboxing cost. In most applications this difference is negligible compared to the flexibility ArrayList provides.
  • Multi-dimensionality — arrays support true multi-dimensional forms directly (int[][]), whereas the equivalent with ArrayList requires nesting (ArrayList<ArrayList<Integer>>), which is less memory-efficient and more verbose.

Rule of thumb: use a plain array when the size is fixed and known up front and you need maximum raw performance (or need primitives without boxing overhead); use ArrayList (or another List implementation) for essentially everything else, since the flexibility and rich API usually outweigh the small performance difference.

Q8. If you were designing a phone directory (contact list), what data structure would you use, and why?

This is a design/reasoning question with no single correct answer — the interviewer wants to see how you weigh tradeoffs based on the required operations. A reasonable answer walks through the actual access patterns:

  • If the dominant operation is looking up a contact by name (or phone number) — a HashMap<String, Contact> keyed by name (or normalized phone number) gives O(1) average-case lookup, insertion, and deletion.
  • If the dominant operation is displaying contacts in alphabetical order (e.g. an address-book-style UI) — a TreeMap<String, Contact> keeps entries continuously sorted by key at the cost of O(log n) operations instead of O(1), trading a bit of raw speed for always-available ordering.
  • If you need BOTH fast lookup AND to occasionally display a sorted view — keep a HashMap as the primary store for O(1) lookups, and sort a snapshot (via Collections.sort() or a stream) only when a sorted view is actually needed for display, rather than paying the TreeMap ordering cost on every single insert (this mirrors the HashMap-vs-TreeMap tradeoff discussion in Part 3).
  • If contacts need to support prefix search (e.g. "show all contacts starting with 'Sm'" as the user types) — a Trie (prefix tree) is the specialized structure built exactly for this, offering efficient prefix lookups that a HashMap or TreeMap can't provide directly.
public class Contact {
    private String contactName;
    private String phoneNumber;
    // constructor, getters, equals/hashCode omitted for brevity
}
 
public class PhoneDirectory {
    // O(1) average lookup by name -- good default choice for a general-purpose directory
    private final Map<String, Contact> contactsByName = new HashMap<>();
 
    public void addContact(Contact contact) {
        contactsByName.put(contact.getContactName(), contact);
    }
 
    public Contact findByName(String contactName) {
        return contactsByName.get(contactName);
    }
 
    // sort only when actually needed for display, rather than maintaining
    // sorted order continuously
    public List<Contact> getContactsSortedByName() {
        List<Contact> sortedContacts = new ArrayList<>(contactsByName.values());
        sortedContacts.sort(Comparator.comparing(Contact::getContactName));
        return sortedContacts;
    }
}

Object-Oriented Design: Elevator System

Q9. Design an elevator system. What classes would you create, and how would they interact?

Problem: This is a classic OOP system-design exercise. The interviewer is evaluating how you decompose a real-world system into classes with clear responsibilities, not looking for one specific "correct" answer. A good response identifies the core entities, their state, their behavior, and how they collaborate.

Core entities

  • Elevator — represents a single elevator car. Tracks its current floor, direction of travel (up/down/idle), and the set of floors it has been requested to stop at.
  • ElevatorController (or ElevatorSystem) — coordinates multiple Elevator instances, deciding which elevator should respond to a given request (e.g. the nearest one already moving in the right direction).
  • Request — represents a single call: either an external hall call (a person on floor N pressing 'up' or 'down') or an internal car call (a passenger inside the elevator pressing a destination floor button).
  • Door — represents the elevator's door state (open/closed) and behavior (open, close, with appropriate safety checks like obstruction detection).
  • Direction — an enum (UP, DOWN, IDLE) used by both Elevator and Request to express travel direction.

A minimal class sketch

public enum Direction {
    UP, DOWN, IDLE
}
 
public class Request {
    private final int requestedFloor;
    private final Direction requestedDirection; // null for internal car-button requests
 
    public Request(int requestedFloor, Direction requestedDirection) {
        this.requestedFloor = requestedFloor;
        this.requestedDirection = requestedDirection;
    }
 
    public int getRequestedFloor() {
        return requestedFloor;
    }
 
    public Direction getRequestedDirection() {
        return requestedDirection;
    }
}
import java.util.TreeSet;
 
public class Elevator {
    private final int elevatorId;
    private int currentFloor;
    private Direction currentDirection = Direction.IDLE;
 
    // sorted set of floors this elevator still needs to visit, so the
    // nearest pending stop is always easy to find
    private final TreeSet<Integer> pendingStops = new TreeSet<>();
 
    public Elevator(int elevatorId, int startingFloor) {
        this.elevatorId = elevatorId;
        this.currentFloor = startingFloor;
    }
 
    public void addStop(int floor) {
        pendingStops.add(floor);
        updateDirection();
    }
 
    private void updateDirection() {
        if (pendingStops.isEmpty()) {
            currentDirection = Direction.IDLE;
        } else if (pendingStops.first() < currentFloor) {
            currentDirection = Direction.DOWN;
        } else if (pendingStops.last() > currentFloor) {
            currentDirection = Direction.UP;
        }
    }
 
    public void moveOneStep() {
        if (currentDirection == Direction.UP) {
            currentFloor++;
        } else if (currentDirection == Direction.DOWN) {
            currentFloor--;
        }
        if (pendingStops.contains(currentFloor)) {
            pendingStops.remove(currentFloor); // arrived -- open doors, etc.
        }
        updateDirection();
    }
 
    public int getCurrentFloor() {
        return currentFloor;
    }
 
    public Direction getCurrentDirection() {
        return currentDirection;
    }
 
    public int getElevatorId() {
        return elevatorId;
    }
}
import java.util.List;
 
public class ElevatorController {
    private final List<Elevator> managedElevators;
 
    public ElevatorController(List<Elevator> managedElevators) {
        this.managedElevators = managedElevators;
    }
 
    // simple "nearest available elevator" dispatch strategy
    public Elevator handleRequest(Request incomingRequest) {
        Elevator bestElevator = null;
        int shortestDistance = Integer.MAX_VALUE;
 
        for (Elevator candidate : managedElevators) {
            int distance = Math.abs(candidate.getCurrentFloor() - incomingRequest.getRequestedFloor());
 
            // prefer an idle elevator, or one already moving toward the request
            boolean isSuitable = candidate.getCurrentDirection() == Direction.IDLE
                    || candidate.getCurrentDirection() == incomingRequest.getRequestedDirection();
 
            if (isSuitable && distance < shortestDistance) {
                shortestDistance = distance;
                bestElevator = candidate;
            }
        }
 
        if (bestElevator != null) {
            bestElevator.addStop(incomingRequest.getRequestedFloor());
        }
        return bestElevator;
    }
}

Points worth discussing out loud in the interview

  • Dispatch strategy is the interesting algorithmic core of this problem — the simple "nearest suitable elevator" strategy shown above is a reasonable starting point, but real systems use more sophisticated algorithms (e.g. minimizing average wait time across all pending requests, or the classic SCAN/LOOK disk-scheduling-style algorithms, which elevator systems are named after).
  • Concurrency matters in a real implementation: multiple hall-call buttons could be pressed simultaneously by different people, and the elevators themselves move independently — this naturally maps onto a design with each Elevator potentially running on (or being controlled by) its own thread, with the ElevatorController needing thread-safe request handling.
  • Extensibility: keeping Direction as its own type, and Request decoupled from Elevator, makes it straightforward to later add features like priority requests (e.g. a fire-emergency override), express elevators that skip certain floors, or capacity limits — without having to restructure the core classes.
  • This question is really testing class decomposition and clear separation of responsibilities more than any single "correct" algorithm — an interviewer will often follow up by asking you to extend the design (e.g. "now add support for a weight limit") to see how cleanly your structure accommodates change.

String Handling: Conceptual Questions

Q10. What is the difference between String, StringBuilder, and StringBuffer?

All three represent sequences of characters, but they differ fundamentally in mutability and thread-safety:

  • String — immutable (see Part 1). Every "modification" (concatenation, substring, etc.) actually creates a brand new String object, leaving the original unchanged. This makes String inherently thread-safe (no mutable state to corrupt), and safe to share and cache (e.g. the String pool), but potentially expensive if you're building up a string through many small modifications in a loop, since each one allocates a new object.
  • StringBuilder — mutable, and NOT thread-safe (no internal synchronization). This makes it the right choice for building up or modifying a string within a single thread — for example, inside a loop that appends many pieces together — since it can grow an internal buffer in place rather than allocating a new object on every change.
  • StringBuffer — mutable, functionally almost identical to StringBuilder, but every method is synchronized, making it safe to share across multiple threads. This synchronization overhead makes StringBuffer measurably slower than StringBuilder in the (very common) single-threaded case.
// Inefficient: creates a new String object on every iteration (n concatenations = n new objects)
String inefficientResult = "";
for (int i = 0; i < 1000; i++) {
    inefficientResult += i; // creates a brand new String each time
}
 
// Efficient: StringBuilder mutates its internal buffer in place
StringBuilder efficientResult = new StringBuilder();
for (int i = 0; i < 1000; i++) {
    efficientResult.append(i);
}
String finalResult = efficientResult.toString();

Practical guidance: default to StringBuilder for any single-threaded string-building work (which is the overwhelming majority of cases — even a method with purely local StringBuilder usage doesn't need StringBuffer, since no other thread can see that local variable). Reach for StringBuffer only in the genuinely rare case where a single mutable string buffer must be shared and modified across multiple threads.

Q11. What is the difference between Hashtable, HashMap, and ConcurrentHashMap?

These represent an evolution of the same basic idea (a hash-based key-value map), with different thread-safety tradeoffs:

  • Hashtable — the original, legacy implementation (present since JDK 1.0). Thread-safe via coarse-grained synchronization: every single method is synchronized on the whole table, so only one thread can access the Hashtable at all (for read OR write) at any given moment. Does not permit null keys or null values.
  • HashMap — the modern general-purpose implementation (added in Java 1.2, as part of the Collections Framework). NOT thread-safe at all — concurrent unsynchronized access can corrupt internal state (see the discussion in Part 1). Faster than Hashtable in single-threaded use due to the lack of synchronization overhead. Permits one null key and multiple null values.
  • ConcurrentHashMap — added in Java 5 (java.util.concurrent) specifically to give HashMap-like functionality with GOOD concurrent performance, unlike Hashtable's all-or-nothing single lock. It achieves this through fine-grained internal locking (or, in modern JDKs, largely lock-free operations via CAS), so multiple threads can read and write different parts of the map concurrently with minimal contention. Does not permit null keys or null values (this restriction exists specifically to avoid ambiguity in concurrent get() calls about whether a null result means "absent" or "present with a null value").

Practical guidance: never use Hashtable in new code — it's a legacy holdover with no advantage over the alternatives. Use plain HashMap for single-threaded (or externally-synchronized, if truly necessary) access, and ConcurrentHashMap whenever a map genuinely needs to be shared and modified by multiple threads.

Dynamic Programming: Decode Ways

Q12. How many ways can a string of digits be decoded into letters, given A=1, B=2, ..., Z=26?
LeetCode: Decode Ways ↗

Problem: A message containing letters A-Z can be encoded into numbers using the mapping 'A' -> "1", 'B' -> "2", ..., 'Z' -> "26". Given a string of digits, determine how many different ways it can be decoded back into letters. Example: "12" can decode as "AB" (1, 2) or "L" (12), so the answer is 2. "226" can decode as "BZ" (2, 26), "VF" (22, 6), or "BBF" (2, 2, 6), so the answer is 3.

Approach: This is a classic 1D dynamic programming problem (see Part 3's DP pattern). At each position in the string, you have up to two choices: decode the current single digit as one letter (valid only if it's not '0'), or decode the current digit together with the previous one as a two-digit letter (valid only if that two-digit number is between 10 and 26). The number of ways to decode up to position i depends only on the number of ways to decode up to positions i-1 and i-2 — a textbook DP recurrence.

public class DecodeWays {
 
    public static int countDecodings(String digitString) {
        if (digitString == null || digitString.isEmpty() || digitString.charAt(0) == '0') {
            return 0; // a leading zero can never be validly decoded
        }
 
        int stringLength = digitString.length();
        // waysToDecode[i] = number of ways to decode the first i characters
        int[] waysToDecode = new int[stringLength + 1];
        waysToDecode[0] = 1; // one way to decode an empty prefix: decode nothing
        waysToDecode[1] = 1; // already validated the first character isn't '0' above
 
        for (int position = 2; position <= stringLength; position++) {
            char currentDigit = digitString.charAt(position - 1);
            char previousDigit = digitString.charAt(position - 2);
 
            // option 1: decode the current character alone, as a single-digit letter (1-9)
            if (currentDigit != '0') {
                waysToDecode[position] += waysToDecode[position - 1];
            }
 
            // option 2: decode the previous and current characters together, as a two-digit letter (10-26)
            int twoDigitValue = (previousDigit - '0') * 10 + (currentDigit - '0');
            if (twoDigitValue >= 10 && twoDigitValue <= 26) {
                waysToDecode[position] += waysToDecode[position - 2];
            }
        }
 
        return waysToDecode[stringLength];
    }
 
    public static void main(String[] args) {
        System.out.println(countDecodings("12"));  // 2  ("AB" or "L")
        System.out.println(countDecodings("226")); // 3  ("BZ", "VF", "BBF")
        System.out.println(countDecodings("06"));  // 0  (leading zero is never valid)
        System.out.println(countDecodings("10"));  // 1  ("J" only -- "1" then "0" is invalid alone)
    }
}

Complexity: O(n) time (a single pass through the string), O(n) space for the waysToDecode array (which can be optimized down to O(1) space, since each step only ever looks back at the two immediately preceding values).
