Question 46: Design a distributed job scheduler (like a cron service) that can run millions of scheduled jobs reliably across a cluster.

Difficulty: Hard Asked by: Amazon, Google, Microsoft

Answer: The core challenge isn’t scheduling itself — it’s guaranteeing exactly-once execution (or at least “effectively-once” with idempotent jobs) when multiple scheduler nodes exist for high availability, since two nodes must never both fire the same job.

Architecture: 1. Job store: Persist job definitions (cron expression or one-off timestamp, payload, target handler) in a durable DB, partitioned/sharded by job_id hash for horizontal scale. 2. Leader-based partition ownership: Rather than every scheduler node polling the entire job table (causing duplicate firing and lock contention), partition jobs across scheduler nodes (e.g., consistent hashing of job_id to node) and use a coordination service (ZooKeeper/etcd) for leader election and partition rebalancing when nodes join/leave. 3. Locking on fire: Even with partitioning, use a short-lived distributed lock (SELECT ... FOR UPDATE SKIP LOCKED in Postgres, or a Redis SETNX with TTL) at the moment of firing, so a rebalance race condition can’t cause double-firing.

-- Postgres: efficiently claim due jobs without blocking other workers
SELECT * FROM scheduled_jobs
WHERE next_run_at <= NOW() AND status = 'PENDING'
ORDER BY next_run_at
LIMIT 100
FOR UPDATE SKIP LOCKED;
  1. Execution decoupling: The scheduler’s job is to trigger, not execute — on firing, publish a message to Kafka/SQS for the actual job handler to consume and run, so a slow/failing job doesn’t block the scheduler’s own loop.
  2. Missed-job recovery: If a scheduler node is down when a job was due, on recovery/rebalance the new owner must detect and fire (or explicitly skip, per job config) overdue jobs — this requires storing next_run_at durably, not computing it only in memory.
  3. Idempotency contract: Since retries/edge cases can cause at-least-once delivery, require every job handler to be idempotent (keyed by job_id + scheduled_time), rather than trying to engineer perfect exactly-once semantics, which is prohibitively complex in a distributed system.

Key Takeaway for Leads: The recurring theme across all reliable-scheduling designs is: don’t chase exactly-once execution guarantees at the infrastructure level — design for at-least-once delivery plus idempotent consumers. This is a cheaper, more robust engineering trade-off, and it’s the answer that shows real distributed-systems maturity in an interview.

Question 47: Design WhatsApp/a chat application — focus on message delivery guarantees, online presence, and read receipts.

Difficulty: Hard Asked by: Amazon, Google, Microsoft

Answer: Connection layer: Persistent WebSocket (or MQTT, which is more bandwidth-efficient for mobile/battery-constrained clients) connection per active client, held by a stateless-except-for-connection “gateway” service. Client identity maps to (userId -> gatewayInstanceId) in a shared registry (Redis) so any backend service can find which gateway node currently holds a user’s live connection.

Message send flow: 1. Sender’s client sends message to its connected gateway. 2. Gateway persists the message to a durable message store (partitioned by conversation ID) and assigns a monotonic sequence number per conversation — critical for correct ordering/read-receipt tracking even with out-of-order network delivery. 3. Gateway looks up the recipient’s connection registry: if online, push directly via that recipient’s gateway node (pub/sub between gateway nodes, e.g., Redis Pub/Sub or a Kafka topic keyed by userId); if offline, queue for delivery on next connect and optionally trigger a push notification (APNs/FCM).

Delivery/read receipt state machine: SENT (persisted server-side) → DELIVERED (recipient’s device acknowledged receipt) → READ (recipient opened the conversation). Each state transition is itself a small message flowing back to the sender, and must be idempotent (a duplicate “delivered” ack shouldn’t cause issues).

public enum MessageStatus { SENT, DELIVERED, READ }

@KafkaListener(topics = "message-acks")
public void onAck(MessageAck ack) {
    // idempotent: re-processing the same ack is a no-op if status already >= ack.status
    messageStore.updateStatusIfHigher(ack.getMessageId(), ack.getStatus());
}

Online presence: Rather than a naive “broadcast presence change to all contacts” (which doesn’t scale — a popular user’s presence flicker would fan out to millions), use a pull-on-view model (client requests presence only for currently-visible contacts/open chats) combined with a short heartbeat-based TTL in Redis (presence:userId key with a 30s TTL, refreshed by the client) — absence of the key means offline, avoiding explicit disconnect-handling edge cases (crashed clients, network drops) entirely.

Key Takeaway for Leads: The design decision to trade “perfectly accurate for everyone always” (broadcast presence) for “accurate enough, computed on demand” (pull-based, TTL-based) is a classic Lead-level trade-off — recognizing where eventual/approximate correctness is a perfectly acceptable, dramatically cheaper choice is exactly what differentiates a scalable design from a theoretically-clean but unscalable one.

Question 48: Design a distributed rate-limited API for a public developer platform (like Stripe/Twilio’s API), including per-customer quotas and burst handling.

Difficulty: Medium Asked by: Amazon, Google, Stripe-style fintech

Answer: Building on the token-bucket rate limiter fundamentals: a public API platform needs multi-tier limiting — global (protect the whole platform from any single misbehaving customer), per-customer (contracted quota tiers — free/pro/enterprise), and per-endpoint (expensive endpoints like bulk export get a stricter limit than cheap read endpoints).

Design: 1. Centralized limit store: Redis cluster holding token-bucket state per (customerId, endpoint) key, since limiting must be consistent across all API gateway instances — a per-instance in-memory limiter would let a customer trivially exceed limits by spreading requests across gateway nodes. 2. Fail-open vs fail-closed decision: If Redis itself is unavailable, decide explicitly: fail-closed (reject all requests) protects backend systems but causes a full platform outage from a Redis blip; fail-open (allow all requests) risks a backend overload during exactly the moment Redis is unhealthy. My usual recommendation for a public API: fail-open for a short grace period with aggressive alerting, since a Redis outage should be rare and short, and a full platform outage is worse for customer trust than a brief unlimited-traffic window. 3. Response contract: Return standard rate-limit headers (X-RateLimit-Limit, X-RateLimit-Remaining, Retry-After) so client SDKs can implement backoff automatically — this is a real developer-experience requirement, not just an internal implementation detail.

@Component
public class RateLimitFilter extends OncePerRequestFilter {
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        String customerId = extractApiKeyCustomer(req);
        RateLimitResult result = rateLimiter.check(customerId, req.getRequestURI());
        res.setHeader("X-RateLimit-Limit", String.valueOf(result.getLimit()));
        res.setHeader("X-RateLimit-Remaining", String.valueOf(result.getRemaining()));
        if (!result.isAllowed()) {
            res.setHeader("Retry-After", String.valueOf(result.getRetryAfterSeconds()));
            res.sendError(429, "Rate limit exceeded");
            return;
        }
        chain.doFilter(req, res);
    }
}
  1. Quota tier changes without redeploys: Store per-customer overrides in a fast-lookup config store (not hardcoded), so support/sales can adjust an enterprise customer’s limits without an engineering deploy.

Key Takeaway for Leads: The fail-open/fail-closed decision is a genuine business risk trade-off, not a purely technical one — as a Lead, I’d explicitly loop in product/business stakeholders on this specific choice rather than making it unilaterally, since it directly trades off platform protection against customer-facing availability.

Question 49: Design a large-scale log aggregation and search system (like an internal Splunk/ELK) ingesting terabytes of logs per day from thousands of services.

Difficulty: Hard Asked by: Amazon, Google, Microsoft, Goldman Sachs

Answer: Pipeline stages: 1. Collection: Lightweight agents (Fluent Bit/Filebeat) on each host/pod tail log files or read from stdout, doing minimal processing (just batching and forwarding) to keep the collection footprint cheap on every single host. 2. Buffering/transport: Kafka as the durable buffer between collection and processing — critical because log volume is extremely bursty (an incident often causes a log volume spike at exactly the moment the pipeline needs to keep up), and Kafka absorbs that burst without dropping data, unlike a direct-to-Elasticsearch write path which can fall over under burst load. 3. Processing/enrichment: A stream processor (Kafka Streams/Flink) parses structured fields, enriches with metadata (service name, region, k8s pod labels), and routes to appropriate indices — this is also where PII redaction/masking should happen for compliance, never left to the ingestion or storage layer as an afterthought. 4. Storage/indexing: Elasticsearch (or OpenSearch) with time-based index rotation (daily/hourly indices) so old indices can be efficiently deleted/archived by simply dropping the whole index rather than a row-by-row delete — critical at this data volume. 5. Hot/warm/cold tiering: Recent indices (last few days) on fast SSD-backed hot nodes for interactive search performance; older indices moved to cheaper warm/cold storage tiers (Elasticsearch’s Index Lifecycle Management) automatically, and eventually to object storage or deleted per retention policy.

Cost/scale considerations to raise explicitly in the interview: at terabyte/day scale, indexing everything at full fidelity is often prohibitively expensive — discuss sampling strategies for high-volume, low-value logs (e.g., successful health-check pings) versus guaranteed full retention for error-level logs and audit-relevant events, plus configurable per-service log levels to control volume at the source rather than filtering it out downstream after paying the ingestion cost.

Key Takeaway for Leads: A common trap in this design is treating “ingest everything, index everything, keep forever” as the default — a Lead should proactively raise the cost/value trade-off (this system’s infrastructure bill scales directly with total log volume) and drive log-volume discipline across engineering teams as an ongoing practice, not just build bigger storage to absorb unchecked growth.

Question 50: Design a ride-sharing driver-matching system (like Uber) — focus on geospatial matching at scale.

Difficulty: Hard Asked by: Amazon, Google, Microsoft

Answer: Core problem: given a rider’s location, find the nearest available drivers in a bounded radius, at massive scale, with sub-second latency, while driver locations are constantly updating (every few seconds per active driver).

Geospatial indexing approach: Use a geohashing scheme (or Uber’s own H3 hexagonal grid system, which handles the “distance near a boundary” distortion issues of naive geohash rectangles better) to divide the map into cells. Each driver’s current cell ID is maintained in a fast in-memory store (Redis with geospatial commands GEOADD/GEORADIUS, or a custom H3-cell-keyed structure).

// Redis GEO commands abstract this well for a first-pass design
redisTemplate.opsForGeo().add("active-drivers", 
    new Point(driverLng, driverLat), driverId);

// Find drivers within 3km of the rider
GeoResults<RedisGeoCommands.GeoLocation<Object>> nearby = redisTemplate.opsForGeo()
    .radius("active-drivers", new Circle(new Point(riderLng, riderLat), new Distance(3, Metrics.KILOMETERS)));

Location update pipeline: Driver apps send location pings every 3-5 seconds via a lightweight endpoint (or WebSocket) — at scale (millions of active drivers), this write volume is the real bottleneck, so writes go to a fast in-memory geo-index (Redis, sharded by geographic region) rather than a relational DB, with only periodic/sampled snapshots persisted to a durable store for historical/analytics purposes.

Matching algorithm beyond pure distance: Real systems don’t just pick the geographically nearest driver — they factor in driver’s current direction of travel, estimated time-to-pickup (which accounts for road network, not straight-line distance), driver rating/acceptance-rate, and surge/supply-demand balancing across nearby cells. This is typically a scoring function combining several weighted signals rather than a single nearest-neighbor query, and it often runs as a separate matching service consuming the geo-index as one input among several.

Handling matching race conditions: Multiple riders requesting near-simultaneous matches to the same nearby driver — the match/accept step needs an atomic claim (similar to the inventory-reservation pattern: UPDATE drivers SET status='MATCHED' WHERE id=? AND status='AVAILABLE' with the affected-row-count checked) so exactly one match wins the driver.

Key Takeaway for Leads: This design is a great opportunity to demonstrate you know when to reach for a specialized geospatial data structure/index (H3/geohash + Redis GEO) instead of trying to force a relational database’s lat/long columns with a bounding-box query, which simply doesn’t scale to this write/read volume and latency requirement.

Question 51: Design a distributed lock service that multiple microservice instances can use to prevent duplicate concurrent processing of the same resource.

Difficulty: Medium Asked by: Amazon, Goldman Sachs, JP Morgan

Answer: Options and trade-offs: 1. Redis-based (Redlock or simple SET NX PX): Fast, simple, widely used — acquire a lock via SET key value NX PX ttl, release by comparing value (a unique client token) before deleting, to avoid accidentally releasing another client’s lock that was acquired after your own TTL expired.

public boolean acquireLock(String resourceKey, String clientToken, long ttlMs) {
    String result = redisTemplate.execute((RedisCallback<String>) connection ->
        connection.set(resourceKey.getBytes(), clientToken.getBytes(),
            Expiration.milliseconds(ttlMs), RedisStringCommands.SetOption.SET_IF_ABSENT) ? "OK" : null);
    return "OK".equals(result);
}

public void releaseLock(String resourceKey, String clientToken) {
    String luaScript = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
    redisTemplate.execute(RedisScript.of(luaScript, Long.class), List.of(resourceKey), clientToken);
}

Caveat to raise explicitly: Redis-based locking (even Redlock’s multi-instance variant) isn’t provably safe under all failure/GC-pause scenarios per Martin Kleppmann’s well-known critique — a client can pause (long GC pause, network delay) past the TTL, believe it still holds the lock, and act on stale assumptions while another client has already acquired it. Acceptable for most business use cases (deduplicating a scheduled job, preventing a double-charge retry) where the cost of a rare violation is low; not acceptable for correctness-critical scenarios (e.g., a financial ledger). 2. ZooKeeper-based (ephemeral sequential nodes): Provides much stronger consistency guarantees via a consensus protocol (ZAB), with locks automatically released on session/connection loss (not a fixed TTL guess) — the right choice when correctness matters more than raw throughput/latency, at the cost of operational complexity of running a ZooKeeper ensemble. 3. Database-based (SELECT ... FOR UPDATE or a unique-constraint row): Simplest to reason about if you already have a relational DB in the critical path, piggybacking on the DB’s own transaction guarantees rather than introducing a new distributed system.

Key Takeaway for Leads: The right lock mechanism depends entirely on the cost of a rare correctness violation for that specific use case — I explicitly map this out (business impact of a double-execution) before picking a locking technology, rather than defaulting to “whatever we already use for other things.” This calibrated-risk reasoning is exactly what an interviewer wants to hear instead of a single memorized “use Redlock” answer.

Question 52: Design a fraud detection system for real-time credit card transactions that must approve or decline within 200ms.

Difficulty: Hard Asked by: Goldman Sachs, JP Morgan, Amex-style fintech

Answer: The hard constraint driving the whole design: a 200ms end-to-end budget rules out any synchronous call to a heavyweight ML model serving a full feature-engineering pipeline against a cold data store — everything on the critical path must be pre-computed, cached, or extremely fast.

Architecture: 1. Feature store with pre-computed aggregates: Rather than computing “transactions by this card in the last hour” live from a transactional DB (too slow), maintain rolling aggregates (via a stream processor like Flink/Kafka Streams continuously updating counts/sums in a low-latency store like Redis) — e.g., txn_count_last_1h, total_amount_last_24h, distinct_merchants_last_7d, keyed by card ID, updated incrementally as new transactions stream in. 2. Real-time scoring path: On each incoming transaction, fetch the pre-computed features (single Redis lookup, sub-millisecond), combine with the current transaction’s own attributes, and run a lightweight model (a pre-trained gradient-boosted tree or logistic regression, served via a low-latency in-process or co-located model server — not a heavyweight network call to a separate slow inference cluster) to produce a fraud score within the latency budget.

public FraudDecision evaluate(Transaction txn) {
    CardFeatures features = featureStore.getFeatures(txn.getCardId()); // Redis lookup, <5ms
    FeatureVector vector = FeatureVector.combine(txn, features);
    double score = fraudModel.score(vector); // local model inference, <10ms
    if (score > HARD_DECLINE_THRESHOLD) return FraudDecision.decline();
    if (score > REVIEW_THRESHOLD) return FraudDecision.approveWithFlag(); // async human/secondary review
    return FraudDecision.approve();
}
  1. Rule-based fast-path layer alongside the ML model: Certain hard rules (card reported stolen, transaction from a sanctioned country, amount far exceeding any historical pattern) should be simple, explainable, deterministic checks that short-circuit before even reaching the ML model — both for speed and for regulatory explainability (a declined transaction needs a defensible reason, and “the model said so” is often not sufficient for compliance/dispute-handling purposes).
  2. Async deep analysis for borderline cases: Transactions in a “gray zone” score range are approved immediately (to meet the latency SLA) but flagged for asynchronous, more expensive secondary analysis (a heavier model, or human review), with the ability to retroactively act (block the card, reverse if still reversible) if deep analysis later confirms fraud — accepting a small window of risk in exchange for meeting the hard latency requirement on every transaction.

Key Takeaway for Leads: The single most important design move here is separating “what must happen synchronously within 200ms” from “what can happen asynchronously after the fact” — this is a recurring pattern across every latency-critical financial system design question, and explicitly naming this separation early in your answer signals strong systems thinking to the interviewer.

Question 53: Design a distributed configuration/feature-flag system that can push config changes to thousands of running service instances within seconds, without a redeploy.

Difficulty: Medium Asked by: Amazon, Microsoft, Google

Answer: Requirements to state upfront: near-real-time propagation (seconds, not minutes), must work even if the central config service is briefly unavailable (services shouldn’t crash-loop or freeze if they can’t reach it), and must support targeted rollout (percentage-based, per-tenant, per-region).

Architecture — push vs pull trade-off: - Pull-based (polling): Each service instance periodically polls the config service for updates. Simple, resilient to config-service downtime (services just keep their last-known config), but introduces propagation latency equal to the poll interval, and at thousands of instances, naive polling creates significant load on the config service unless mitigated with caching/ETags. - Push-based (long-poll or streaming, e.g., gRPC streaming or a pub/sub channel): The config service holds an open connection/stream to each client and pushes updates immediately on change — near-instant propagation, but a more complex connection-management problem at scale (similar to the WebSocket fan-out challenge from the chat-app design), and needs careful handling of the “config service is down” case, so clients don’t stall indefinitely without a config.

My recommended hybrid, which is what most production systems (LaunchDarkly, Unleash, internal systems at large tech companies) actually use: long-polling (or gRPC streaming) for near-real-time push, plus a local disk-cached fallback config so a client that can’t reach the config service on startup (or after losing its stream) still boots with a reasonably fresh, locally-persisted last-known-good configuration rather than failing to start or falling back to unsafe hardcoded defaults.

@Component
public class FeatureFlagClient {
    private volatile FlagSnapshot currentSnapshot;

    @PostConstruct
    public void init() {
        currentSnapshot = loadFromLocalCache(); // survive a cold start if config service is down
        streamUpdatesAsync(); // long-poll/stream loop updates currentSnapshot and persists to local cache on each update
    }

    public boolean isEnabled(String flagKey, String tenantId) {
        return currentSnapshot.evaluate(flagKey, tenantId); // percentage rollout / targeting logic evaluated locally, no network call per check
    }
}

Critically: flag evaluation itself must be a local, in-memory, sub-microsecond operation — never a network call per flag check, since flags are often checked on extremely hot code paths (potentially millions of times per second across a fleet).

Key Takeaway for Leads: The “must degrade gracefully if the config service is unreachable” requirement is the part junior designs most often miss — as a Lead, I’d explicitly call out this failure mode in a design review even if the interviewer didn’t ask about it, since a feature-flag system that can bring down the entire fleet during its own outage is strictly worse than not having dynamic config at all.

Question 54: Design a system for processing and settling millions of financial transactions in a nightly batch window, with strict correctness and auditability requirements.

Difficulty: Hard Asked by: Goldman Sachs, JP Morgan, HDFC Bank, ICICI Bank

Answer: Batch settlement systems have fundamentally different design pressures from real-time systems: the SLA is a fixed wall-clock batch window (e.g., must complete between 11 PM and 5 AM), correctness and auditability outrank raw latency, and the system must be able to restart safely from a failure partway through without double-processing or losing records.

Architecture: 1. Chunked, checkpointed processing (Spring Batch is the standard Java tool here): Break the full dataset into chunks (e.g., 1,000 records per chunk), commit a transaction per chunk with a persisted checkpoint of progress — if the job crashes at chunk 4,000 of 10,000, a restart resumes from chunk 4,000, not from zero, and never reprocesses already-committed chunks.

@Bean
public Step settlementStep(JobRepository jobRepository, PlatformTransactionManager txManager) {
    return new StepBuilder("settlementStep", jobRepository)
        .<Transaction, SettlementRecord>chunk(1000, txManager)
        .reader(transactionReader())
        .processor(settlementProcessor())
        .writer(settlementWriter())
        .faultTolerant()
        .retryLimit(3)
        .retry(TransientDataAccessException.class)
        .skipLimit(50)
        .skip(ValidationException.class) // skip and log individually-bad records rather than failing the whole batch
        .build();
}
  1. Idempotent writers: Even with checkpointing, a crash between “write result” and “commit checkpoint” can cause a chunk to be reprocessed — the writer itself must be idempotent (upsert semantics keyed by a natural business key, not blind inserts) so a reprocessed chunk doesn’t create duplicate settlement records.
  2. Parallelization within the window: Partition the dataset (e.g., by account-range or region) and run partitions in parallel across worker nodes (Spring Batch’s partitioning support, or a distributed processing framework) to fit within the fixed batch window as data volume grows — this must be planned for from the start, since a purely single-threaded design that meets today’s SLA will eventually blow through the window as transaction volume grows.
  3. Reconciliation and audit trail: Every processed record generates an immutable audit entry (input state, output state, timestamp, processing job run ID) — in banking, being able to answer “prove that transaction X was settled correctly and show the exact processing lineage” is often a hard regulatory requirement, not an optional nice-to-have.
  4. Pre/post batch validation gates: A pre-batch check (input record count matches expected feed count, checksums match) and a post-batch reconciliation (sum of settled amounts matches sum of input amounts) act as automated correctness gates — the batch should not be considered “successful” on mere completion without exit-criteria validation, since a batch job that runs to completion but silently drops or duplicates a subset of records is a much worse failure mode than one that visibly crashes.

Key Takeaway for Leads: In banking-system interviews specifically, actively bring up reconciliation and audit trail requirements even if not explicitly asked — this is the single biggest differentiator between a generically “correct” batch design and one that would actually pass a real banking architecture review, and interviewers at these firms are listening specifically for this awareness.

Question 55: Design a search autocomplete/typeahead system that returns suggestions within 50ms as a user types.

Difficulty: Medium Asked by: Amazon, Google, Microsoft

Answer: Core data structure: a Trie (prefix tree) is the natural fit — each node represents a character, and traversing to a prefix’s node gives you a subtree of all matching completions. Augment each node with the top-K most popular completions pre-computed and cached at that node, so a query doesn’t need to traverse the entire subtree at request time — it just returns the pre-sorted top-K list stored right at the prefix node.

class TrieNode {
    Map<Character, TrieNode> children = new HashMap<>();
    List<String> topKSuggestions = new ArrayList<>(); // pre-computed, sorted by frequency/relevance
}

public List<String> autocomplete(String prefix) {
    TrieNode node = root;
    for (char c : prefix.toCharArray()) {
        node = node.children.get(c);
        if (node == null) return Collections.emptyList(); // no matches
    }
    return node.topKSuggestions; // O(1) lookup at request time — the expensive work was done at build time
}

Scale considerations: 1. Build offline, serve from a read-optimized snapshot: The trie (with pre-computed top-K per node) is far too expensive to update on every single search event in real time at scale — instead, aggregate search-frequency data in a batch/streaming pipeline (e.g., hourly), rebuild the trie snapshot, and hot-swap the in-memory structure served by the autocomplete API. This trades some short-term freshness for dramatically simpler and cheaper serving-time behavior. 2. Sharding for scale: Partition the trie by first character (or first N characters) across multiple nodes if the full dataset doesn’t fit comfortably in memory on one machine, with a routing layer directing each prefix query to the correct shard. 3. Personalization layer on top: Combine the global popularity-based trie results with a lightweight per-user re-ranking (recent searches, location) applied client-side or in a thin layer after the base trie lookup — keeping the expensive global structure impersonal and cacheable while still delivering a personalized-feeling result. 4. Client-side debouncing: Not a backend concern, but worth mentioning proactively — the client should debounce keystrokes (e.g., wait 100-150ms of typing pause, or at minimum cancel in-flight requests for stale prefixes) to avoid firing a request per keystroke, which both wastes backend capacity and can cause race conditions where a stale response for an earlier, shorter prefix arrives after and overwrites a newer, more specific result.

Key Takeaway for Leads: This design showcases a very common and valuable pattern: shifting expensive computation from request-time to build-time via precomputation, then serving cheaply from a cached snapshot — recognizing when this trade-off is available (data doesn’t need to be second-by-second fresh) is a hallmark of efficient large-scale system design.

Question 56: Design a distributed inventory management system for an e-commerce platform during a flash sale, where thousands of users compete for limited stock simultaneously.

Difficulty: Hard Asked by: Amazon, Flipkart-style e-commerce

Answer: The core failure mode to design against: naive “check stock, then decrement” logic under massive concurrent load either oversells (race condition) or, if you serialize everything through a single DB row lock, creates a severe bottleneck exactly when you have the most concurrent demand (a flash sale is precisely the worst-case scenario for lock contention on a single hot row).

Design: 1. Move the hot-path decrement out of the relational DB into a fast, atomic in-memory operation: Use Redis’s atomic DECR/Lua script to pre-load available stock counts into Redis before the sale starts, and have the initial “can I even attempt to buy this?” check hit Redis, not the DB directly — Redis single-threaded command execution gives you a naturally atomic decrement without DB-level lock contention.

public boolean reserveStock(String productId, int quantity) {
    String luaScript = """
        local current = tonumber(redis.call('get', KEYS[1]) or 0)
        if current >= tonumber(ARGV[1]) then
            redis.call('decrby', KEYS[1], ARGV[1])
            return 1
        else
            return 0
        end
        """;
    Long result = redisTemplate.execute(RedisScript.of(luaScript, Long.class),
        List.of("stock:" + productId), String.valueOf(quantity));
    return result != null && result == 1;
}
  1. Queue the actual order-creation, don’t process it synchronously in the request path: Once Redis confirms a successful reservation, push the actual order-creation/payment flow to an asynchronous queue (Kafka) rather than doing it inline — this decouples “did I successfully claim inventory” (must be instant, since the user is waiting) from “is my order fully processed and paid” (can take a few seconds, communicated via a subsequent status update/websocket push), smoothing the load on downstream systems (payment gateway, order DB) rather than hitting them with a synchronous spike.
  2. Reconciliation between Redis (fast, source of truth for the sale window) and the DB (durable, source of truth long-term): Periodically (and definitely at sale end) reconcile Redis counters against the DB’s actual committed order count to catch any drift from edge cases (a Redis restart mid-sale, a reservation that was never followed by a completed order and needs to be released back).
  3. Queueing/virtual waiting room for extreme demand: For genuinely oversubscribed flash sales (10,000x more demand than stock), consider an explicit virtual waiting room (admit users to the actual purchase flow at a controlled rate) rather than letting all traffic hit the reservation system simultaneously — this is as much a UX/fairness design decision as a technical scaling one, and worth mentioning as a trade-off you’d discuss with product stakeholders.

Key Takeaway for Leads: The move from “the database is the single source of truth for every operation” to “a fast in-memory layer is the real-time source of truth during the hot window, reconciled against the durable DB afterward” is a recurring, high-value pattern for extreme-concurrency scenarios — recognize it and articulate the reconciliation safety net explicitly, since a design without that reconciliation step is incomplete.

Question 57: Design a system to detect and prevent duplicate/spam content submission at scale (e.g., a review or comment platform).

Difficulty: Medium Asked by: Amazon, Google, Microsoft

Answer: Layered defense, from cheapest/fastest to most expensive/thorough — reject early and cheaply wherever possible: 1. Rate limiting per user/IP (token bucket, as covered earlier) as the first, cheapest gate — most naive spam/abuse is high-volume from a small number of sources, and this alone stops a large fraction of it with minimal cost. 2. Exact-duplicate detection via content hashing: Hash (SHA-256 or a normalized-text hash) each submission and check against a recent-submissions cache (Redis, with a reasonable TTL) — catches copy-paste spam cheaply without any heavyweight text analysis. 3. Near-duplicate detection via similarity hashing: For spam that’s slightly modified to evade exact-hash matching (e.g., adding random characters), use a locality-sensitive hashing scheme like SimHash or MinHash — these produce similar hash values for similar text, letting you detect near-duplicates via Hamming distance comparison rather than expensive pairwise text comparison across the entire corpus.

public boolean isNearDuplicate(String content, long simHashThresholdDistance) {
    long contentHash = SimHash.compute(content);
    List<Long> recentHashes = recentSubmissionHashCache.getRecent(userId, timeWindow);
    return recentHashes.stream()
        .anyMatch(hash -> Long.bitCount(hash ^ contentHash) <= simHashThresholdDistance);
}
  1. Behavioral/heuristic signals: Account age, submission velocity, ratio of submissions to account activity, known-spam pattern matching (excessive links, specific phrase patterns) — combined into a spam-likelihood score, similar in spirit to the fraud-scoring approach from the fraud-detection design.
  2. ML-based classification for the remaining ambiguous cases: A trained spam classifier (can run asynchronously, doesn’t need to block the immediate submission response) flags content for review or auto-removal, with human-reviewed feedback looping back to retrain the model over time.
  3. Async, not blocking, for the expensive stages: Accept the submission immediately (good user experience — nobody wants a 2-second delay posting a comment), but run stages 3-5 asynchronously, with the ability to retroactively hide/remove content flagged after the fact — mirroring the “approve fast, deep-analyze async” pattern from the fraud-detection design.

Key Takeaway for Leads: Notice the layered, cheapest-first filtering pattern recurring across many of these designs (spam detection, fraud detection, even cache invalidation’s stampede protection) — explicitly naming this as a deliberate design pattern (“fail fast and cheap, escalate to expensive analysis only for what survives the cheap filters”) in an interview signals that you recognize transferable design principles rather than treating each system as a one-off puzzle.

Question 58: Design a multi-region active-active deployment for a global SaaS application, addressing data consistency and conflict resolution.

Difficulty: Hard Asked by: Amazon, Google, Microsoft

Answer: Why active-active, and the core tension it introduces: Active-active (all regions serve both reads and writes, versus active-passive where only one region writes) gives lower latency for globally-distributed users and higher availability (no single region is a single point of failure) — but it directly reintroduces the CAP theorem trade-off at the regional level: if the same record can be written in two regions concurrently, you need a conflict-resolution strategy, since a network partition between regions will eventually happen.

Approach, layered by data type — not every piece of data needs the same strategy: 1. Data that’s naturally region-scoped (most SaaS data, if partitioned well): If you can partition data by a “home region” (e.g., a customer’s data primarily lives in and is written from their nearest region, replicated to other regions as read-replicas), you avoid true multi-writer conflicts for the majority of data — this is the cheapest and most robust option wherever the business model allows it. 2. Data that’s genuinely globally shared and concurrently written (unavoidable in some domains): Use CRDTs (Conflict-free Replicated Data Types) for data structures that need automatic, mathematically well-defined conflict resolution without coordination (e.g., a global counter using a PN-Counter CRDT, or a collaborative document using an OT/CRDT-based structure) — appropriate when the data model fits a CRDT’s constraints (commutative, associative merge operations). 3. Last-Write-Wins (LWW) with a reliable clock source: Simpler than CRDTs but coarser — attach a timestamp (ideally from a synchronized clock source like Google’s TrueTime-inspired approach, or at minimum a hybrid logical clock, not naive wall-clock time which can skew across regions) to each write, and the latest timestamp wins on conflict. Accept that this can silently lose a legitimate concurrent write — appropriate only where that data loss is genuinely acceptable (e.g., “last viewed timestamp” but not “account balance”). 4. Explicit application-level conflict resolution with audit trail: For business-critical data where silent LWW isn’t acceptable, detect the conflict (via vector clocks or version vectors) and either merge programmatically with domain-specific logic, or surface the conflict for manual/business-rule resolution — more engineering effort, but necessary where correctness genuinely can’t be automatically inferred.

Routing and failover: Global load balancing (DNS-based geo-routing, or an anycast-based approach) directs users to their nearest healthy region; region health checks trigger automatic traffic shifting away from a degraded region.

Key Takeaway for Leads: The most important move in this design is refusing to apply one global consistency strategy to the entire dataset — a Lead should push the team to classify data by its actual consistency requirements (region-scoped vs globally shared, tolerant of loss vs not) and apply the cheapest sufficient strategy per category, rather than either over-engineering CRDTs everywhere or under-engineering LWW everywhere.

Question 59: Design an observability/monitoring platform (metrics, alerting) for a company running hundreds of microservices, including alert fatigue reduction.

Difficulty: Medium Asked by: Amazon, Microsoft, Goldman Sachs

Answer: Metrics pipeline: Services expose metrics (via Micrometer in the Spring Boot ecosystem, in a Prometheus-compatible format) which are scraped (pull-based, Prometheus’s model) or pushed (push-gateway pattern for short-lived batch jobs that don’t live long enough to be scraped) into a time-series database. At hundreds-of-services scale, a single Prometheus instance won’t hold everything — use federation/sharding (Thanos or Cortex/Mimir layered on top of Prometheus) for long-term, globally-queryable storage.

@Timed(value = "order.processing.time", description = "Time to process an order")
public Order processOrder(OrderRequest request) {
    // Micrometer auto-records duration; queryable in Prometheus as order_processing_time_seconds
    return orderService.process(request);
}

The Four Golden Signals (Google SRE framework) as the baseline every service should expose: Latency, Traffic (request rate), Errors (rate), Saturation (resource utilization approaching capacity) — standardizing on these across all services (via a shared metrics library/starter, tying back to the custom-starter pattern discussed earlier) means every team’s dashboards and alerts follow a consistent, comparable shape rather than each team inventing their own metrics from scratch.

Alert fatigue reduction — this is the part interviewers specifically probe for at scale: 1. Alert on symptoms, not causes: Alert on “error rate > 5% for 5 minutes” (a user-facing symptom) rather than alerting on every individual underlying signal that could contribute to it (CPU spike, one pod restart, a single slow query) — the latter creates alert floods where one real incident triggers 20 separate pages. 2. SLO-based alerting (error budgets): Define an explicit Service Level Objective (e.g., 99.9% of requests succeed within 200ms over a rolling 30-day window) and alert based on error budget burn rate rather than a static threshold — a service that’s slightly degraded but well within its monthly error budget shouldn’t page anyone at 3 AM; a service burning its entire monthly budget in an hour absolutely should, even if the instantaneous error rate looks moderate. 3. Alert routing and severity tiers: Not every alert should page a human immediately — distinguish “page now” (customer-facing impact, needs immediate action) from “ticket for business hours” (concerning trend, not urgent) from “dashboard only” (informational), and route accordingly rather than defaulting everything to the highest-urgency channel. 4. Deduplication and grouping: Group related alerts firing simultaneously (e.g., all instances of one service alerting due to one shared root cause like a bad deploy) into a single incident notification rather than N separate pages for what is actually one problem.

Key Takeaway for Leads: Alert fatigue is a genuine, well-documented cause of missed real incidents (on-call engineers desensitized by noisy alerts eventually start ignoring or delaying response to all of them, including the real ones) — as a Lead, treating alert quality/noise as a metric to actively manage and reduce (tracking pages-per-week, false-positive rate) is as important as building the monitoring system itself in the first place.

Question 60: Design a system for real-time collaborative document editing (like Google Docs), focusing on conflict resolution for simultaneous edits.

Difficulty: Hard Asked by: Google, Microsoft, Amazon

Answer: The core problem: multiple users edit the same document simultaneously, each seeing their own edits applied instantly (must feel local/instant, no round-trip wait), while all clients must eventually converge to the same final document state, in an order that preserves each user’s editing intent even though edits were made concurrently against different intermediate document states.

Two established approaches: 1. Operational Transformation (OT): Each edit is represented as an operation (e.g., “insert ‘x’ at position 5”). When the server receives an operation from a client, it transforms that operation against any other operations that were applied concurrently (that the sending client hadn’t yet seen) so that applying the transformed operation produces a consistent result regardless of arrival order. This is what Google Docs historically used — it works well but the transformation functions are notoriously intricate to implement correctly for anything beyond simple text (correct OT for rich formatting, tables, etc. is a significant engineering undertaking). 2. CRDTs (Conflict-free Replicated Data Types) for text, e.g., RGA (Replicated Growable Array) or similar sequence CRDTs: Each character/element gets a unique, globally-ordered identifier (often combining a client ID and a logical clock) at creation time, and the merge rule for concurrent inserts is deterministic and commutative by construction — any two clients merging the same set of operations, in any order, converge to the identical result without needing a central transformation step. This is the approach favored by more recent collaborative editors (and libraries like Yjs, Automerge) because the merge logic, while still non-trivial, is more composable and testable than hand-rolled OT transformation functions.

// Simplified CRDT-style character identity for ordering
public record CharId(long clientId, long logicalClock) implements Comparable<CharId> {
    public int compareTo(CharId other) {
        // deterministic total order regardless of arrival sequence at any replica
        return logicalClock != other.logicalClock
            ? Long.compare(logicalClock, other.logicalClock)
            : Long.compare(clientId, other.clientId);
    }
}

Architecture around the core algorithm: - Local-first application: Each client applies its own edits to a local replica instantly (no waiting for server round-trip), then asynchronously syncs operations to the server/other clients — this is what makes editing feel instant regardless of network latency. - Central server’s role shifts from “the authority that resolves every edit” (in OT) to more of a relay/persistence layer (in CRDT-based systems, since the merge logic is deterministic regardless of where it runs) — though a server-side canonical copy is still valuable for persistence, offline-client catch-up, and access control enforcement. - Presence and cursor sharing: A separate, much simpler real-time channel (WebSocket broadcast, ephemeral — doesn’t need CRDT-level durability guarantees) shows other users’ live cursor positions, since this is inherently transient UI state, not durable document content. - Persistence and snapshotting: Periodically compact/snapshot the full operation history into a materialized document state (rather than requiring every client to replay the entire edit history from document creation to reconstruct current state), analogous to event-sourcing snapshot patterns.

Key Takeaway for Leads: This is one of the hardest system design questions in the standard rotation specifically because the “obvious” naive approach (last-write-wins on the whole document, or a simple server-side lock) fails the actual product requirement (simultaneous, non-blocking, intent-preserving editing) — the value in your answer is recognizing that this requires a fundamentally different class of algorithm (OT/CRDT), not just applying general distributed-systems patterns you’d use elsewhere, and being able to articulate at a conceptual level why naive approaches don’t work here.
